# 02. Context Engineering — CLAUDE.md

In the previous lecture, we discussed **what context is**. Now the next question is:

> How do we engineer that context so that an AI coding agent consistently gives us better results?

This is where **Context Engineering** comes in.

## The Problem

Suppose we have a large codebase and ask an AI coding agent to:

- write new code,
- debug existing code,
- review a pull request,
- understand the architecture,
- or research something about the codebase.

Without additional context, the agent has to repeatedly discover things such as:

- How is this project structured?
- What coding standards do we follow?
- Which libraries/frameworks should it use?
- What patterns should it avoid?
- How should tests be written?
- What commands should it run?

As developers, we already know many of these things.

We also have our own **standards, conventions, preferences, and constraints**.

We don't want to repeat all of this information in every prompt.

For example:

```text
Use Python 3.12.
Use pytest for testing.
Follow the repository pattern already used in /src/repositories.
Never log PII.
Use async database calls.
Don't introduce new dependencies without asking.
```

Instead of repeatedly putting these instructions into every query, we need a place where the coding agent can find this persistent context.

For Claude Code, one important mechanism for doing this is **CLAUDE.md**.

---

# CLAUDE.md

`CLAUDE.md` is a Markdown file used to provide Claude Code with persistent instructions and project context.

Instead of repeatedly writing:

```text
Follow this coding style...
Use these commands...
Don't do this...
Our architecture works like this...
```

we can document those instructions once and allow Claude Code to use them while working on the project.

You can think of it as:

> **A README written for the coding agent rather than only for humans.**

---

## Global vs Project-Level Instructions

There are two useful levels of context.

### 1. Global / User-Level

These are instructions that apply across projects.

For example:

```text
Prefer simple implementations over clever abstractions.
Explain important architectural decisions.
Do not modify unrelated files.
```

These represent our general preferences when working with an AI coding agent.

### 2. Project-Level

These instructions are specific to a particular codebase.

For example:

```text
Backend: FastAPI
Database: PostgreSQL
ORM: SQLAlchemy
Testing: pytest

All API routes must live under /api/v1.
Business logic should not be placed inside route handlers.
```

These instructions describe how **this particular project** should be handled.

---

# What Should CLAUDE.md Contain?

A useful mental model is to organize context into five categories:

1. Identity
2. Rules
3. Format
4. Knowledge
5. Tools

These don't have to literally become five headings in every `CLAUDE.md`. They are a framework for thinking about what context the agent needs.

---

## 1. Identity

**Who should the model behave as?**

Identity gives the model a useful role or perspective.

Example:

```text
You are working as a senior Python engineer reviewing a fintech backend.
Prioritize correctness, security, maintainability, and clear code.
```

Identity can influence how the model approaches a problem.

However, identity alone is usually not enough.

```text
You are an expert programmer.
```

is much less useful than giving the agent concrete project knowledge and rules.

---

## 2. Rules

Rules describe **what the agent must do and must not do**.

Example:

```text
Always check database queries for SQL injection risks.

Never log passwords, access tokens, or PII.

Do not introduce a new dependency without approval.

Run tests before considering a task complete.
```

Rules are especially important because they define the **constraints and guardrails** of the project.

If we need to reduce the amount of context, important safety and project constraints should generally be among the **last things we remove**.

---

## 3. Format

Format defines **how we want the output to be structured**.

Example:

```text
When reviewing code, structure the response as:

1. Critical Issues
2. Security Issues
3. Maintainability Issues
4. Suggested Improvements
```

Or:

```text
When proposing code changes, mention the files that need to change before writing code.
```

Format instructions make responses more predictable and easier to consume.

---

## 4. Knowledge

Knowledge contains information about the project that the model needs in order to make good decisions.

For example:

```text
Authentication uses JWT access tokens.

Redis is used only for caching.

PostgreSQL is the source of truth.

All external payment operations go through PaymentService.

The /legacy directory should not be used for new development.
```

This is one of the most important parts of context engineering.

The better the model understands the environment in which it is operating, the less it has to **rediscover** that information.

---

## 5. Tools

Tools describe the capabilities, commands, scripts, or workflows available to the agent.

Example:

```text
Run tests:

pytest tests/

Run linting:

ruff check .

Run type checking:

mypy src/

Start the development server:

uvicorn app.main:app --reload
```

Instead of making the agent guess how the project works, explicitly tell it which tools and commands are available.

# How Do We Create a Good CLAUDE.md?

Usually, we don't know the perfect `CLAUDE.md` from day one.

We may start with rough notes about:

- architecture,
- coding standards,
- commands,
- important constraints,
- common mistakes,
- and project conventions.

We can ask an LLM to help organize these notes into a structured `CLAUDE.md`.

But the first version should **not be considered final**.

A better process is iterative:

```text
Start with a small CLAUDE.md
        ↓
Run the agent on a real task
        ↓
Observe where it fails
        ↓
Understand why it failed
        ↓
Add one targeted instruction
        ↓
Run the task again
        ↓
Repeat
```

In other words:

> **Don't try to predict every possible rule upfront. Let real failures tell you what context is missing.**

This prevents `CLAUDE.md` from becoming a huge collection of unnecessary instructions.

---

# The "Right Altitude" Principle

A useful principle when writing instructions is to write them at the **right level of abstraction**.

Instructions should be:

> **Specific enough to guide behavior, but general enough to remain useful in situations you did not explicitly anticipate.**

Consider this rule:

```text
Never edit user_service.py.
```

This may fix one specific failure, but it might become incorrect later.

A better rule might be:

```text
Avoid modifying stable domain services unless the task explicitly requires a change to their behavior.
```

The second instruction captures the **reasoning behind the rule**, making it applicable to more situations.

Too specific:

```text
Don't change line 47 of auth.py.
```

Too vague:

```text
Be careful with authentication.
```

Better altitude:

```text
Preserve existing authentication and authorization behavior unless the task explicitly requires changing it.
```

The goal is to encode **useful heuristics**, not just patches for individual failures.

---

# Avoid Rule Explosion

One common mistake is continuously adding instructions.

After some time, we might end up with:

```text
Always do X.
Never do Y.
Use A.
Prefer B.
Never use B when C happens.
Always use B when D happens.
```

Eventually, rules can become redundant or even contradictory.

More instructions do **not automatically mean better performance**.

The agent now has to determine which instructions are relevant and how conflicting instructions should be resolved.

So instead of writing a massive instruction file from the beginning:

```text
Prompt
   ↓
Real Task
   ↓
Observe Failure
   ↓
Add Targeted Rule
   ↓
Retest
   ↓
Repeat
```

Periodically clean up the instructions as well:

- remove obsolete rules,
- merge duplicate rules,
- resolve contradictions,
- replace overly specific rules with better heuristics.

---

# Important Note: CLAUDE.md Is Not Simply RAG

A tempting mental model is:

```text
CLAUDE.md
   ↓
Split into chunks
   ↓
Embed everything
   ↓
Retrieve top 3 chunks for every query
```

But we should be careful with this analogy.

Claude Code has its own mechanisms for loading project instructions and memory. We should **not assume that `CLAUDE.md` is simply converted into embeddings and queried as a top-k RAG system**.

The broader context-engineering idea is still useful:

> Give the agent the most relevant context it needs while avoiding unnecessary context.

For very large projects, instead of putting everything into one giant file, we can organize instructions closer to where they are relevant and reference supporting documentation when appropriate.

# Markdown vs XML

Context can be structured using formats such as **Markdown** and **XML-style tags**.

Markdown works well for human-readable project instructions:

```md
## Testing

Use pytest for all backend tests.

## Security

Never log authentication tokens.

## Database

Use SQLAlchemy for database access.
```

XML-style tags can be useful when we want strong semantic boundaries inside prompts:

```xml
<rules>
Never log PII.
Do not modify database schemas without approval.
</rules>

<project_context>
The backend uses FastAPI and PostgreSQL.
</project_context>
```

Neither format is automatically "better."

The important thing is that the context is:

- clear,
- structured,
- relevant,
- consistent,
- and easy to maintain.

# Similar Concepts Across Coding Agents

Different coding agents use different mechanisms for persistent project instructions.

```text
Claude Code       → CLAUDE.md
Cursor            → .cursor/rules/
GitHub Copilot    → .github/copilot-instructions.md
Windsurf          → project/workspace instruction mechanisms
Cross-tool usage  → AGENTS.md
```

The filenames and exact behavior differ, but the underlying idea is similar:

> **Store important context close to the environment where the agent is working.**

# Context Depends on the Task

Different tasks benefit from different kinds of context.

### Classification

Examples are often extremely useful:

```text
INPUT → OUTPUT
INPUT → OUTPUT
INPUT → OUTPUT
```

This is **few-shot prompting**.

Instead of only explaining a classification rule, we show the model examples of the expected mapping.

### Reasoning Tasks

For reasoning-heavy tasks, provide:

- relevant facts,
- constraints,
- assumptions,
- intermediate artifacts,
- examples of desired reasoning patterns when appropriate.

We should be careful with thinking of this as simply asking the model for its hidden **chain of thought**.

The goal of context engineering is to provide the model with the **information and structure required to reason well**, not necessarily to request private internal reasoning.

### Structured Output

When exact output structure matters, provide the expected schema or template directly.

For example:

```json
{
  "severity": "HIGH | MEDIUM | LOW",
  "file": "string",
  "issue": "string",
  "recommendation": "string"
}
```

Examples, schemas, prefixes, and templates can strongly constrain the output format.

---

# Core Idea

Context engineering is not about writing the **largest possible prompt**.

It is about providing the **right information, at the right time, in the right structure**.

A good context system answers questions such as:

```text
Who should the agent act as?
        ↓
What rules must it follow?
        ↓
What does it need to know?
        ↓
What tools can it use?
        ↓
What should the output look like?
```

`CLAUDE.md` is one practical way of applying these ideas to coding agents.

The goal is not:

> "Tell the model everything."

The goal is:

> **Give the model the context it needs to make the right decision without forcing it to rediscover that context on every task.**
