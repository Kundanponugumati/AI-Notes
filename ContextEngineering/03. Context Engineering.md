# 03. Context Engineering — Tools, Function Calling & MCP

## 1. Tools

### What are tools, and why do we need them?

At its core, an **LLM is a next-token predictor**.

Given some context, it predicts the most likely next token and continues this process to generate a response.

This means an LLM by itself has some important limitations:

- It may not have **up-to-date information**.
- It cannot directly interact with the outside world.
- It may be unreliable for tasks requiring **exact or deterministic results**.
- It cannot directly access databases, APIs, files, browsers, etc.

### Example

Suppose we ask:

`7321 × 1234`

An LLM may generate the correct answer, but it is still generating tokens probabilistically rather than behaving like a calculator.

Instead, we can give the LLM access to a **calculator tool**.

The LLM decides:

> "This requires exact arithmetic, so I should use the calculator."

The calculator performs the deterministic computation and returns the result.

### Why tools matter

Without tools:

**User → LLM → Response**

The LLM is primarily generating text based on its learned knowledge and current context.

With tools:

**User → LLM → Tool → External World → Tool Result → LLM → Response**

Tools allow an LLM to access capabilities outside the model itself.

Examples include:

- Calculator → exact calculations
- Web search → current information
- Weather API → live weather
- Database → application data
- File system → read/write files
- Email API → send/read emails
- Calendar API → create/manage events

### Key Idea

> **LLM + Tools = a system that can observe external information and take actions.**

Tools are one of the major building blocks for turning an LLM-based application into an **agentic system**.

---

# 2. Tool / Function Calling Lifecycle

A typical tool-calling lifecycle has five stages:

**Describe → Decide → Call → Return → Respond**

## Step 1: Describe

First, we tell the model which tools are available.

Usually, this is done using a **tool schema**.

A schema describes things such as:

- Tool name
- What the tool does
- Required arguments
- Argument types

Example:

```text
Tool: get_weather

Description:
Get the current weather for a location.

Arguments:
location: string
```

The tool descriptions become part of the context available to the model.

---

## Step 2: Decide

The model analyzes the user's request and decides whether a tool is required.

Example:

```text
User:
What's the weather in Chennai?
```

The model might decide:

```text
Use tool: get_weather

Arguments:
location = "Chennai"
```

An important point:

> The LLM usually **requests** the tool call. It does not execute the tool itself.

---

## Step 3: Call

The application/orchestrator receives the tool request and actually executes it.

Conceptually:

```python
result = get_weather("Chennai")
```

The execution happens outside the LLM.

---

## Step 4: Return

The tool produces a result.

Example:

```text
Temperature: 31°C
Condition: Cloudy
```

The application adds this tool result back into the conversation/context.

So the LLM now sees something conceptually like:

```text
User:
What's the weather in Chennai?

Assistant:
Call get_weather("Chennai")

Tool:
Temperature: 31°C
Condition: Cloudy
```

---

## Step 5: Respond

Finally, the LLM uses the returned information to produce a natural-language response:

```text
It's currently 31°C and cloudy in Chennai.
```

### Easy way to remember

**Describe → Decide → Call → Return → Respond**

or:

**Know tools → Choose tool → Execute tool → Get result → Answer user**

---

# 3. The Problem with Many Tools

Tool calling works very well when we only have a small number of tools.

For example:

```text
LLM
 ├── Calculator
 ├── Weather
 └── Search
```

But real-world AI systems may have **dozens, hundreds, or even thousands of tools**.

As the number of tools grows, several problems appear:

- More tool schemas consume more context.
- Choosing the correct tool becomes harder.
- Integrating tools from different systems becomes complicated.
- Every provider may expose tools differently.
- Maintaining integrations becomes expensive.

This creates an **integration problem**.

That leads us to MCP.

---

# 4. MCP — Model Context Protocol

## What is MCP?

**MCP = Model Context Protocol**

MCP is an open protocol originally introduced by **Anthropic** for connecting AI applications to external tools and data sources through a standardized interface.

A useful mental model is:

> **MCP is a standard interface between AI applications and external capabilities.**

It aims to reduce the need to build custom integrations for every model/application and every external system.

---

# 5. Why MCP?

Imagine we have:

- **M AI applications/models**
- **N external systems/tool providers**

Without a common protocol, we may end up building many custom integrations.

Conceptually:

```text
LLM/App 1 ── Tool System 1
LLM/App 1 ── Tool System 2
LLM/App 1 ── Tool System 3

LLM/App 2 ── Tool System 1
LLM/App 2 ── Tool System 2
LLM/App 2 ── Tool System 3
```

This can approach an:

**M × N integration problem**

MCP introduces a standardized boundary.

```text
AI Application
      │
  MCP Client
      │
   MCP Protocol
      │
  MCP Server
      │
External Systems
```

Instead of every application understanding every custom integration, both sides can implement the MCP standard.

Conceptually, this can reduce the integration problem toward:

**M + N**

> Note: M + N is a useful conceptual simplification. Real production integration complexity depends on the systems involved.

---

# 6. MCP Client

The **MCP client** lives on the AI application/host side.

Its job is to communicate with MCP servers using the MCP protocol.

At a high level, an AI application may:

1. Receive a user message.
2. Send relevant context/tool information to the LLM.
3. Receive a request to use a tool.
4. Route that request to the appropriate MCP server.
5. Receive the result.
6. Add the result back into the model's context.
7. Continue until a final response can be produced.

Conceptually:

```text
User
 ↓
AI Application / Host
 ↓
LLM
 ↓
Tool needed
 ↓
MCP Client
 ↓
MCP Server
 ↓
External System
 ↓
Result
 ↓
MCP Client
 ↓
LLM
 ↓
Final Response
```

### Important distinction

The **LLM** performs language understanding/reasoning and may decide that a capability should be used.

The surrounding **application/host + MCP client** handles communication and orchestration with the MCP server.

---

# 7. MCP Server

An **MCP server** exposes capabilities to MCP clients in a standardized way.

Three important primitives are:

### 1. Tools

Tools are **actions/functions that can be invoked**.

Examples:

```text
send_email()
search_database()
create_calendar_event()
get_weather()
```

Think:

> **Tool = Do something**

---

### 2. Resources

Resources expose **data/context** that an AI application can access.

Examples:

```text
Files
Database records
Documentation
Application data
Repository contents
```

Think:

> **Resource = Read/get something**

---

### 3. Prompts

Prompts are **reusable prompt templates/workflows** exposed by a server.

For example:

```text
summarize_document
review_code
generate_report
```

Think:

> **Prompt = Reusable instruction/template**

# 9. Tool Calling vs MCP

These concepts are related but **not the same thing**.

### Tool / Function Calling

Tool calling is the general mechanism where an LLM can indicate:

> "I want this function/tool to be called with these arguments."

Example:

```text
get_weather(location="Chennai")
```

### MCP

MCP provides a **standardized protocol for AI applications to discover and interact with external capabilities and context**.

So:

> **Tool calling = model requests a capability**

> **MCP = standardized infrastructure/protocol for exposing and connecting capabilities**

MCP does not replace the fundamental tool-calling idea. It helps standardize how AI applications connect to external systems.

# 10. JIT — Just-In-Time Context

A major challenge with context engineering is deciding:

> **What information should we put into the context, and when?**

Suppose we have 1,000 tools.

Loading descriptions of all 1,000 tools into every prompt would be:

- Expensive
- Token-heavy
- Distracting
- Potentially harmful to tool-selection accuracy

Instead, we can use **Just-In-Time (JIT) context**.

### Core idea

> Don't load everything upfront. Retrieve the relevant context/capabilities when they are needed.

Instead of:

```text
Context =
Tool 1
Tool 2
Tool 3
...
Tool 1000
User Query
```

we want something closer to:

```text
User Query
    ↓
Find relevant capabilities
    ↓
Load only relevant context/tools
    ↓
LLM
```

For example:

```text
User: "What's the weather in Chennai?"

1000 available tools
        ↓
Retrieve relevant tools
        ↓
get_weather
get_forecast
        ↓
Provide only these to the LLM
```

This keeps the model's working context more focused.

### Why JIT matters

JIT context can help with:

- Context-window efficiency
- Lower token usage
- Reduced distraction
- Better tool selection
- Scaling to large tool ecosystems

### Revision line

> **JIT = Load the right context at the right time instead of loading everything upfront.**

# 11. ReAct Framework

**ReAct = Reason + Act**

ReAct is an agent pattern where the model alternates between reasoning about what to do and taking actions through tools.

Conceptually:

```text
Reason
  ↓
Act
  ↓
Observe
  ↓
Reason
  ↓
Act
  ↓
Observe
  ↓
Final Answer
```

### Example

User asks:

```text
What's the weather in Chennai,
and should I carry an umbrella?
```

Conceptually, the agent may do:

```text
Reason:
I need current weather information.

Act:
Call weather tool.

Observation:
Rain probability = 85%

Reason:
There is a high probability of rain.

Final Answer:
Rain is likely, so carrying an umbrella would be useful.
```

The important pattern is:

**Reason → Act → Observe → Repeat**

The model does not need to know everything beforehand. It can gather information through tools as the task progresses.
